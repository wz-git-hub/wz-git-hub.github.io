watchdog_bookhub.sh 新增 WorkBuddy 每日 07:00 守护步骤 +（2026-11-20）

发表于2026-11-20|更新于2026-11-21|自动化运维
|阅读量:

当天最关键的判断：watchdog 的「心跳正常」不能当单实例凭证，得另加一把原子锁。

早上把需求落进 .workbuddy/scripts/watchdog_bookhub.sh。这个脚本每 30 秒跑一轮；要新增的是步骤 4——每天 7 点查 WorkBuddy 在不在跑、没在跑就拉起来。顺手排查时发现：有两个 watchdog 进程同时在跑（PID 14004 创建于 11-14 17:49，PID 35768 创建于 11-19 23:49），两边心跳都「正常」。

一、WorkBuddy 守护逻辑

判断是否运行：tasklist //FI "IMAGENE eq WorkBuddy.exe" //NH + grep -qi。Electron 主进程/渲染/GPU 同名，任一存在即算在跑；主进程死了子进程会随之退出。

触发条件：HM >= 700（不是 == 700）。watchdog 每 30s 一轮撞不准整点，且睡眠/关机错过 7 点后唤醒会自动补检。

状态文件 tmp/wb.check：格式为 日期 已确认(0/1) 尝试次数 时间戳

  • 当天一旦确认「在运行」就整天不再动（用户主动关掉不会被反复拉起）
  • 启动失败每 10 分钟重试，最多 3 次，之后 ALERT 熔断

启动命令：cmd //c start "" "$WB_EXE"——注意空 "" 是 start 的窗口标题位，不能省。然后 20×2s 轮询检测，最多等 40s（< 120s 心跳阈值）。

刹车机制：tmp/.wb_off 存在则完全不动作。

二、实测验证与踩坑

用 notepad.exe 做替身测过（真 WorkBuddy 正在跑，关了对话就断）：

  • 进程不在 → 启动 ✓ 2s 内检测到
  • 已确认 → 不再动作 ✓ SKIP
  • 伪造次数=3 → 熔断 ✓ 只 ALERT 一次，第二次 WAIT

踩的坑：

  1. charmap.exe 不能当替身——Win10+ 是 UWP 转发，进程名不是 charmap.exe。notepad / mstsc 才是标准 win32 GUI。
  2. 从 Bash 调 PowerShell 被安全策略硬拦（Invoking PowerShell from Bash bypasses PowerShell security checks）。检测逻辑不能用 Get-CimInstance 内联，改用纯 bash 的 mkdir 原子锁。
  3. 已在运行的 WorkBuddy 再 start 一次：单实例锁生效，进程数不变，无副作用。

三、双实例并存问题排查与修复

心跳只能判「多久没动静」，两个实例被同时拉起时双方看到的是同一个旧心跳，于是都进来了。修法是在心跳之外加 mkdir 原子锁 tmp/.watchdog.lock：

  • mkdir 成功 = 抢到锁，进循环
  • 失败则看锁目录 mtime：<120s 退出；≥120s 先 rmdir 再抢，抢不到退出
  • 循环里每轮 touch "$LOCK" 续命

实测第二次 mkdir 正确失败。重启步骤（以后换脚本要照做）：

  1. Get-CimInstance Win32_Process | ?{$_.CommandLine -like '*watchdog_bookhub*'} 拿到全部 PID（含两层 bash -c 壳）
  2. Stop-Process -Force 全杀
  3. 删 tmp/watchdog.heartbeat 与 tmp/.watchdog.lock
  4. Start-ScheduledTask -TaskName BlogWatchdog
  5. 验：心跳 30s 内刷新 + .watchdog.lock mtime 跟着动 + 进程 3 个（2 壳 + 1 脚本）

四、当前状态与遗留

pid=150291，11:22:53 启动。日志已出现 [OK] WorkBuddy 07:00 检查：已在运行；wb.check = 2026-11-20 1 0 ...。测试脚本保留在 .workbuddy/tmp/test_wb_step.sh（notepad 替身，手动回归用）。

遗留：真 WorkBuddy 没被杀过（关了对话就断），所以「进程不在 → 启动」这条分支只靠 notepad 测过；下次维护窗口再补一次真实拉起验证。
